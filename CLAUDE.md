# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Beat The Scam (https://beatthescam.com) is a UK consumer-protection site: plain-English scam guides + a free AI scam checker. It is a **bespoke Python static-site generator** — not Next.js, Hugo, or Jekyll. The entire site is generated by `scripts/build.py` reading JSON content and rendering through one HTML template into `dist/`. The dynamic surfaces are **five Netlify Functions** (`check-scam`, `subscribe`, `confirm-subscribe`, `unsubscribe`, `csp-report`) — all under `netlify/functions/`.

## Commands

```bash
pip install -r requirements-claude.txt   # one-time deps (build needs only stdlib + optional Pillow/minifiers)

python3 scripts/build.py                  # rebuild the whole site into dist/ (run from repo root)
```

There is **no unit-test suite and no linter for the static build** — the build is the verification step. The CI pipelines sanity-check a build by asserting `dist/index.html`, `dist/robots.txt`, `dist/_redirects` exist and `dist/guides/` has ≥50 subdirectories — do the same locally after changing `build.py`. Two extra checks DO exist: (1) the **content accuracy gate** (`scripts/content_gate.py`) runs in front of every generation path, and its live self-test is `scripts/gate_selftest.py` — run it after any gate change via the **`Gate self-test`** GitHub Action (`.github/workflows/gate-selftest.yml`, manual `workflow_dispatch`, uses the existing `ANTHROPIC_API_KEY` secret) or locally with `ANTHROPIC_API_KEY=… python3 scripts/gate_selftest.py`; (2) the **Netlify Functions now have a `package.json`** (`@netlify/blobs`), so they are the only part of the repo with a JS dependency.

## Architecture

**The build pipeline IS the application.** `content/posts.json` + `content/site.json` + `content/affiliates.json` → `scripts/build.py` → `dist/`. `templates/base.html` is the single page shell; `make_base()` fills its `{{placeholder}}` tokens. Page renderers (`render_home`, `render_post`, `render_category_page`, `render_check_page`, …) build HTML strings, and `build()` at the bottom of `build.py` orchestrates everything and writes every file in `dist/`.

**`dist/` is committed to git AND is exactly what Netlify serves** — there is no build step on Netlify for the static site (build command is blank; `dist/` is published as-is). The one thing Netlify *does* build is the Functions bundle: because `package.json` now exists, Netlify installs the functions' deps (`@netlify/blobs`) when bundling them — this does not touch `dist/`. Consequences:
- A content/template/style change only goes live once you run `python3 scripts/build.py` **and commit the regenerated `dist/`**. Pushing source without rebuilding ships nothing.
- **Never hand-edit anything in `dist/`** — `build()` regenerates the entire directory (it `rmtree`s `dist/` first). This includes `_redirects`, `robots.txt`, `sitemap.xml`, `rss.xml`, `search.json`, `ads.txt`, `llms.txt`, `humans.txt`, `.well-known/security.txt`, `404.html`, and per-post OG images.

**Post schema** — each object in `content/posts.json`: `slug`, `title`, `description`, `hero`, `date` (`YYYY-MM-DD`), `category`, `keywords` (list), `sections` (list of `[heading, body]` pairs), `faq` (list of `[question, answer]` pairs). `posts.json` is the single source of truth; categories, schema, related guides, search index, and sitemap all derive from it.

**Categories are driven by three dicts at the top of `build.py`**: `CATEGORY_CANON` (raw label → canonical slug normalisation), `CATEGORY_LABELS` (slug → display name), `CATEGORY_DESCRIPTIONS`. To add/rename/merge a category, edit these — do not touch rendered output. `CATEGORY_CANON` also auto-emits the category 301s in `dist/_redirects`.

**Redirects are split across two mechanisms (important gotcha):** `netlify.toml` `[[redirects]]` blocks do **not** apply at the edge here except the *grandfathered* `/api/check-scam` → function rewrite (status 200) and the `/*` → `404.html` catch-all. This exception does **not** generalise: a **newly added** toml `[[redirects]]` rule is silently ignored at the edge — confirmed 2026-06-09 when `/api/subscribe` 404'd from toml while `/.netlify/functions/subscribe` resolved. So **every redirect/rewrite you add — category 301s, article 301s, AND new `/api/*` → function rewrites — must live in `dist/_redirects`**, which `build()` auto-generates (the `/api/subscribe` 200 rewrite is emitted at the top of the `_redirects` block, since a `200` rewrite must precede any catch-all to win). Category/article 301s derive from `CATEGORY_CANON` and the `ARTICLE_REDIRECTS` dict (maps a dead slug → replacement slug, or `__CAT__:<cat>` → category page). When you delete/rename a guide, add its old slug to `ARTICLE_REDIRECTS` so inbound links 301 instead of 404.

**The AI scam checker** (`netlify/functions/check-scam.js`) is the first of five Netlify Functions. It is a hardened proxy to the Anthropic API: per-IP rate limiting (10/min), origin allow-listing, input length caps, verdict/confidence enum validation, and reporting links restricted to an **allow-list of official UK reporting domains** (`gov.uk`, `police.uk`, `fca.org.uk`, …, matched by host/subdomain) so a prompt-injected message can't surface an attacker link. Rate limiting + a **global daily spend cap** (`DAILY_CALL_CAP = 2000` Anthropic calls/UTC-day) are backed by **Netlify Blobs** (durable, shared across instances) with a graceful fallback to an in-memory limiter if Blobs is unavailable (the spend cap fails open). It reads `ANTHROPIC_API_KEY` from Netlify env and uses model `claude-haiku-4-5-20251001` (same model as content generation). The page calls it via the `/api/check-scam` rewrite.

**The newsletter is double opt-in**, split across two functions. The sitewide capture band (rendered in `templates/base.html` between `</main>` and the footer, so it appears on every page) POSTs to `/api/subscribe`. **`subscribe.js`** (step 1) validates the request and emails an HMAC-signed **confirmation** link — it does **NOT** add the address to the Resend Audience yet, and returns `{ok:true, pending:true}` (the front-end then says "check your inbox to confirm"). **`confirm-subscribe.js`** (step 2, route `/api/confirm-subscribe`) is reached when the user clicks that link: **GET renders a confirm page only (never mutates** — scanner/prefetch-safe), and **POST adds the contact** to the Resend Audience (`POST /audiences/{id}/contacts`) **and** sends the branded welcome email (From `alerts@updates.beatthescam.com`, Reply-To `hello@beatthescam.com`). This stops anyone subscribing a third party's address. Confirm tokens sign `"confirm:<email>"` so they are NOT interchangeable with unsubscribe tokens (which sign the bare email). Same hardening as the checker: per-IP rate limit, origin allow-list, email + required-consent validation, off-screen honeypot. Both functions read **`RESEND_API_KEY`, `RESEND_AUDIENCE_ID` and `UNSUBSCRIBE_SECRET`** from Netlify env — **all three now required for signup** (the secret signs the confirm link; missing any returns `500 "Service not configured"`). Routed via `dist/_redirects`, not `netlify.toml` (see the redirect gotcha above).

**Unsubscribe** (`netlify/functions/unsubscribe.js`, route `/api/unsubscribe`) closes the compliance loop. The welcome email (sent by `confirm-subscribe.js`) carries a `List-Unsubscribe` / `List-Unsubscribe-Post: List-Unsubscribe=One-Click` header (RFC 8058) **and** a visible body link, both pointing at an HMAC-signed, per-recipient URL. Design choices that matter (and which `confirm-subscribe.js` deliberately mirrors): **GET only renders a confirm page — it never mutates** (so email link-prefetchers/security scanners, which GET every link, can't auto-unsubscribe people); **POST performs the unsubscribe** (Gmail/Yahoo's one-click button POSTs; our confirm form POSTs) by PATCHing the Resend contact to `unsubscribed:true` — the same *global* suppression that future Broadcasts honour. The HMAC key is **`UNSUBSCRIBE_SECRET`** (e.g. `openssl rand -hex 32`), now shared by both the unsubscribe token (signs bare email) and the subscribe-confirm token (signs `"confirm:<email>"`); with it unset, signup fails closed (no forgeable token is ever minted). Note: Resend's managed `{{{RESEND_UNSUBSCRIBE_URL}}}` token is **Broadcasts-only** and is NOT substituted by the `/emails` API — which is why the welcome email self-hosts unsubscribe while future **Broadcasts** get it automatically from Resend.

**CSP report collector** (`netlify/functions/csp-report.js`, route `/api/csp-report`) is the fifth function — it ingests `Content-Security-Policy` violation reports (the CSP `report-uri`/`report-to` point at it). See the CSP note under Deploy.

**Two scheduled content pipelines** (`.github/workflows/`): `daily-publish.yml` (05:07 UTC, generates from the queue) and `daily-search-console.yml` (05:23 UTC, fills Search Console content gaps). Both: call Claude → append to `posts.json` → `build.py` → commit `dist/` → push → auto-tweet. They are serialised via a shared `concurrency: content-pipeline` group because both regenerate `sitemap.xml` from `posts.json`. Each has a rebase-conflict recovery path that snapshots `content/*`, hard-resets to `origin/main`, re-merges posts **by slug** via `scripts/merge_new_posts.py` (never merging `dist/`, since it is derived), and rebuilds.

## Deploy

Push to `main` → Netlify auto-deploys `dist/` (~30s). The Netlify publish directory must be set to `dist` **in the dashboard**, not just `netlify.toml`. `netlify.toml` owns the security headers — note the CSP intentionally allows `'unsafe-inline'` in `script-src` because GA4 and AdSense inject inline scripts; do not "tighten" it without removing those.

**Consent (UK/EEA):** ad + analytics consent is collected by **Google's certified CMP** (AdSense → Privacy & messaging, the "European regulations message"), which drives Google **Consent Mode** (both "advertising" and "analytics" consent-mode toggles are enabled in the dashboard). `assets/app.js` **defers** to it: when a TCF CMP is present (`window.__tcfapi`/`window.googlefc`), the custom cookie banner stays hidden (no double prompt) and the footer "Cookie settings" reopens the CMP; the **custom banner is only a fallback** for regions where Google's message isn't shown. If the CMP is ever CSP-blocked, allow-list `fundingchoicesmessages.google.com` (mind the netlify.toml-headers-at-edge gotcha — Section 20 of `docs/project.md`).
