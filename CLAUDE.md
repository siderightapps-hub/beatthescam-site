# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Beat The Scam (https://beatthescam.com) is a UK consumer-protection site: plain-English scam guides + a free AI scam checker. It is a **bespoke Python static-site generator** — not Next.js, Hugo, or Jekyll. The entire site is generated by `scripts/build.py` reading JSON content and rendering through one HTML template into `dist/`. The dynamic surfaces are **five Netlify Functions** (`check-scam`, `subscribe`, `confirm-subscribe`, `unsubscribe`, `csp-report`) — all under `netlify/functions/`.

## Editorial scope (2026-06-15): video discontinued

YouTube Shorts + TikTok video production has been **discontinued** for Beat the Scam — it built neither domain authority nor backlinks for a search/reference asset, and the manual time goes to the operator's main bet (the "31 Years" YouTube channel). ## Commands

```bash
pip install -r requirements-claude.txt   # one-time deps (build needs only stdlib + optional Pillow/minifiers)

python3 scripts/build.py                  # rebuild the whole site into dist/ (run from repo root)
```

There is **no unit-test suite and no linter for the static build** — the build is the verification step. The CI pipelines sanity-check a build by asserting `dist/index.html`, `dist/robots.txt`, `dist/_redirects` exist and `dist/guides/` has ≥50 subdirectories — do the same locally after changing `build.py`. Two extra checks DO exist: (1) the **content accuracy gate** (`scripts/content_gate.py`) runs in front of every generation path, and its live self-test is `scripts/gate_selftest.py` — run it after any gate change via the **`Gate self-test`** GitHub Action (`.github/workflows/gate-selftest.yml`, manual `workflow_dispatch`, uses the existing `ANTHROPIC_API_KEY` secret) or locally with `ANTHROPIC_API_KEY=… python3 scripts/gate_selftest.py`; (2) the **Netlify Functions now have a `package.json`** (`@netlify/blobs`) + a committed **`package-lock.json`**, so they are the only part of the repo with a JS dependency. **Supply chain (2026-06-22):** `requirements-claude.txt` is upper-bounded, and `.github/dependabot.yml` (npm + pip + github-actions) + `.github/workflows/codeql.yml` (CodeQL SAST for JS + Python) run in CI. **(2026-06-24:** every GitHub Action is pinned to a full commit SHA (with a `# vN` comment so Dependabot still tracks it), the search-console pipeline installs from the pinned `requirements-claude.txt` instead of unpinned, and both content pipelines' rebase-conflict recovery now **preserves freshly-written claim manifests** across the `git reset --hard`.)

**Source canon + claim manifests + weekly audit (editorial accuracy layer).** The gate derives its allow-lists (phone numbers, reporting emails) from the **verified canon `content/sources.json`** — the single source of truth, also rendered as the on-page "Report this scam" block by `build.py` (`load_sources`/`report_block`). On a gate PASS, each generation path writes a per-guide **claim manifest** to `content/manifests/<slug>.json` (an audit record of the high-stakes claims the gate detected — phones, absolutes, entities, non-canon reporting emails, legislation, dated events — NOT a bibliography; the model has no internet, so it never cites). `scripts/audit_corpus.py` re-audits the whole corpus on demand; the **`Weekly editorial audit`** Action (`.github/workflows/weekly-audit.yml`, `scripts/audit_digest.py`) digests recent manifests' flag-tier claims and emails them for human review. The gate BLOCKS the dangerous classes upfront; legislation / dated-event / non-canon-source are FLAG-tier (recorded + reviewed, never blocking). **After a second editorial audit (2026-06-24)** the gate also BLOCKS **CRA misclassification** (ClearScore/CallCredit presented as a UK credit reference agency — the three are Experian, Equifax, TransUnion) and **National Fraud Database wrong-routing** (it is a Cifas service — direct readers to a Cifas Protective Registration), and FLAGs US-style "fraud alert on your credit file" (the UK mechanism is Cifas Protective Registration) and blanket "HMRC never texts/emails/links you" (HMRC runs genuine SMS/email campaigns and genuine texts can carry gov.uk links).

## Architecture

**The build pipeline IS the application.** `content/posts.json` + `content/site.json` + `content/affiliates.json` → `scripts/build.py` → `dist/`. `templates/base.html` is the single page shell; `make_base()` fills its `{{placeholder}}` tokens. Page renderers (`render_home`, `render_post`, `render_category_page`, `render_check_page`, …) build HTML strings, and `build()` at the bottom of `build.py` orchestrates everything and writes every file in `dist/`.

**`dist/` is committed to git AND is exactly what Netlify serves** — there is no build step on Netlify for the static site (build command is blank; `dist/` is published as-is). The one thing Netlify *does* build is the Functions bundle: because `package.json` now exists, Netlify installs the functions' deps (`@netlify/blobs`) when bundling them — this does not touch `dist/`. Consequences:
- A content/template/style change only goes live once you run `python3 scripts/build.py` **and commit the regenerated `dist/`**. Pushing source without rebuilding ships nothing.
- **Never hand-edit anything in `dist/`** — `build()` regenerates the entire directory (it `rmtree`s `dist/` first). This includes `_redirects`, `robots.txt`, `sitemap.xml`, `rss.xml`, `search.json`, `ads.txt`, `llms.txt`, `humans.txt`, `.well-known/security.txt`, `404.html`, and per-post OG images.

**Post schema** — each object in `content/posts.json`: `slug`, `title`, `description`, `hero`, `date` (`YYYY-MM-DD`), `category`, `keywords` (list), `sections` (list of `[heading, body]` pairs), `faq` (list of `[question, answer]` pairs). `posts.json` is the single source of truth; categories, schema, related guides, search index, and sitemap all derive from it.

**Categories are driven by three dicts at the top of `build.py`**: `CATEGORY_CANON` (raw label → canonical slug normalisation), `CATEGORY_LABELS` (slug → display name), `CATEGORY_DESCRIPTIONS`. To add/rename/merge a category, edit these — do not touch rendered output. `CATEGORY_CANON` also auto-emits the category 301s in `dist/_redirects`.

**Redirects are split across two mechanisms (important gotcha):** `netlify.toml` `[[redirects]]` blocks do **not** apply at the edge here except the *grandfathered* `/api/check-scam` → function rewrite (status 200) and the `/*` → `404.html` catch-all. This exception does **not** generalise: a **newly added** toml `[[redirects]]` rule is silently ignored at the edge — confirmed 2026-06-09 when `/api/subscribe` 404'd from toml while `/.netlify/functions/subscribe` resolved. So **every redirect/rewrite you add — category 301s, article 301s, AND new `/api/*` → function rewrites — must live in `dist/_redirects`**, which `build()` auto-generates (the `/api/subscribe` 200 rewrite is emitted at the top of the `_redirects` block, since a `200` rewrite must precede any catch-all to win). Category/article 301s derive from `CATEGORY_CANON` and the `ARTICLE_REDIRECTS` dict (maps a dead slug → replacement slug, or `__CAT__:<cat>` → category page). When you delete/rename a guide, add its old slug to `ARTICLE_REDIRECTS` so inbound links 301 instead of 404.

**The AI scam checker** (`netlify/functions/check-scam.js`) is the first of five Netlify Functions. It is a hardened proxy to the Anthropic API: per-IP rate limiting (10/min), origin allow-listing, input length caps, verdict/confidence enum validation, and reporting links restricted to an **allow-list of official UK reporting domains** (`gov.uk`, `police.uk`, `fca.org.uk`, …, matched by host/subdomain) so a prompt-injected message can't surface an attacker link. Rate limiting + a **global daily spend cap** (`DAILY_CALL_CAP = 2000` Anthropic calls/UTC-day) are backed by **Netlify Blobs** (durable, shared across instances) with a graceful fallback to an in-memory limiter if Blobs is unavailable (the spend cap fails open). **Hardened 2026-06-24:** the Blobs counters are now **atomic** (compare-and-set via etag, so concurrent requests can't bypass the limit), the per-IP key is a **salted hash** (raw IPs are never stored — privacy), a non-allow-listed `Origin` is **rejected** (403, not merely CORS-hidden), the request body is **size-capped before `JSON.parse`**, the Anthropic fetch has a **20s `AbortController` timeout** (→504), and **every** response (incl. errors/limits) carries `Cache-Control: no-store`. It reads `ANTHROPIC_API_KEY` from Netlify env and uses model `claude-haiku-4-5-20251001` (same model as content generation). The page calls it via the `/api/check-scam` rewrite.

**The newsletter is double opt-in**, split across two functions. The sitewide capture band (rendered in `templates/base.html` between `</main>` and the footer, so it appears on every page) POSTs to `/api/subscribe`. **`subscribe.js`** (step 1) validates the request and emails an **opaque (encrypted) confirmation** link — it does **NOT** add the address to the Resend Audience yet, and returns `{ok:true, pending:true}` (the front-end then says "check your inbox to confirm"). **`confirm-subscribe.js`** (step 2, route `/api/confirm-subscribe`) is reached when the user clicks that link: **GET renders a confirm page only (never mutates** — scanner/prefetch-safe), and **POST adds the contact** to the Resend Audience (`POST /audiences/{id}/contacts`) **and** sends the branded welcome email (From `alerts@updates.beatthescam.com`, Reply-To `hello@beatthescam.com`). This stops anyone subscribing a third party's address. Confirm tokens are **opaque / encrypted** (AES-256-GCM, replaced the leaky HMAC format 2026-06-25): the email + a **7-day expiry** are sealed under an HKDF key derived from `UNSUBSCRIBE_SECRET`, so a captured link reveals no address (the old `base64url(email).base36(exp).sig` was non-forgeable but the plaintext email was recoverable from any captured URL) and stops working after the expiry. The key is **domain-separated by purpose**, so a confirm token is NOT interchangeable with an unsubscribe token. The functions **dual-parse** — they also accept the legacy dotted HMAC format (discriminator: opaque tokens are **dotless**, legacy tokens contain `.`) so confirm links already in inboxes keep working; the legacy *confirm* branch can be retired once all such links lapse (7-day TTL). `addContact` **reactivates** a previously-unsubscribed contact on a duplicate (PATCH `unsubscribed:false`); to stop a replayed/old confirm link from silently undoing an unsubscribe within the 7-day window, **confirm tokens are now single-use** — consumed in Netlify Blobs on first confirm (released on add-failure so a transient error doesn't burn the link), added 2026-06-24. `confirm-subscribe.js`/`unsubscribe.js` also set their own **security headers** (strict CSP, X-Frame-Options, nosniff, etc.) on HTML responses, because netlify.toml headers don't reliably reach function responses. Same hardening as the checker: per-IP rate limit, **origin rejection** (non-allow-listed `Origin` → 403), email + required-consent validation, off-screen honeypot, plus (2026-06-24) **durable Netlify-Blobs abuse caps** — a per-address daily limit (hashed key) and a global daily send cap — so newsletter-bombing a victim's inbox can't slip past the per-IP limit via rotating IPs. Both functions read **`RESEND_API_KEY`, `RESEND_AUDIENCE_ID` and `UNSUBSCRIBE_SECRET`** from Netlify env — **all three now required for signup** (the secret signs the confirm link; missing any returns `500 "Service not configured"`). Routed via `dist/_redirects`, not `netlify.toml` (see the redirect gotcha above).

**Unsubscribe** (`netlify/functions/unsubscribe.js`, route `/api/unsubscribe`) closes the compliance loop. The welcome email (sent by `confirm-subscribe.js`) carries a `List-Unsubscribe` / `List-Unsubscribe-Post: List-Unsubscribe=One-Click` header (RFC 8058) **and** a visible body link, both pointing at an **opaque (AES-256-GCM encrypted)**, per-recipient URL. Design choices that matter (and which `confirm-subscribe.js` deliberately mirrors): **GET only renders a confirm page — it never mutates** (so email link-prefetchers/security scanners, which GET every link, can't auto-unsubscribe people); **POST performs the unsubscribe** (Gmail/Yahoo's one-click button POSTs; our confirm form POSTs) by PATCHing the Resend contact to `unsubscribed:true` — the same *global* suppression that future Broadcasts honour. The crypto key is **derived (HKDF) from `UNSUBSCRIBE_SECRET`** (e.g. `openssl rand -hex 32`), domain-separated per purpose so unsubscribe and confirm tokens aren't interchangeable; with it unset, signup fails closed (no token is ever minted). `unsubscribe.js` **dual-parses** — it also verifies the legacy bare-email HMAC format (`base64url(email).sig`) — and because legacy unsubscribe links **never expire**, that legacy branch must stay **indefinitely** for compliance (unlike the confirm legacy branch, which lapses with its 7-day TTL). **Do not rotate `UNSUBSCRIBE_SECRET` casually** — it invalidates every live confirm AND unsubscribe link, new and legacy. Note: Resend's managed `{{{RESEND_UNSUBSCRIBE_URL}}}` token is **Broadcasts-only** and is NOT substituted by the `/emails` API — which is why the welcome email self-hosts unsubscribe while future **Broadcasts** get it automatically from Resend.

**CSP report collector** (`netlify/functions/csp-report.js`, route `/api/csp-report`) is the fifth function — it ingests `Content-Security-Policy` violation reports (the CSP `report-uri`/`report-to` point at it). See the CSP note under Deploy.

**Two scheduled content pipelines** (`.github/workflows/`): `daily-publish.yml` (05:07 UTC, generates from the queue) and `daily-search-console.yml` (05:23 UTC, fills Search Console content gaps). Both: call Claude → run the accuracy gate → append to `posts.json` → `build.py`. **Human-review gate (2026-06-25):** they NO LONGER commit to `main` — each opens a **review pull request** (`git checkout -b auto/… → push → gh pr create`, label `auto-content`), so nothing publishes, gets ads, or is tweeted until the operator merges. This satisfies Google's "auto-generated content must be reviewed/curated before it carries ads" policy. **Auto-tweet moved to `tweet-on-publish.yml`** — it fires on `push` to `main` touching `content/posts.json` (i.e. after a PR merge), tweets only the slugs *added* in that push (diff-based), and has two safety nets: a ≤3-slug cap and the existing `tweeted_posts.json` dedupe. The crons are still serialised via the shared `concurrency: content-pipeline` group. Because each cron now branches off fresh `main` and pushes a NEW branch, the old rebase-conflict recovery machinery is gone (no concurrent push to `main` to conflict with). **Prereq enabled (2026-06-25):** the repo setting "Allow GitHub Actions to create and approve pull requests" (Settings → Actions → General) is on, and `permissions: pull-requests/issues: write` are set.

## Deploy

Push to `main` → Netlify auto-deploys `dist/` (~30s). The Netlify publish directory must be set to `dist` **in the dashboard**, not just `netlify.toml`. `netlify.toml` owns the **static-page** security headers (the Netlify Functions set their own — see the newsletter note above) — note the CSP intentionally allows `'unsafe-inline'` in `script-src` because GA4 and AdSense inject inline scripts; do not "tighten" it without removing those. (2026-06-24 the CSP also sets `frame-ancestors 'none'` alongside `X-Frame-Options: DENY`, and `X-XSS-Protection` is now `0` — the legacy auditor is obsolete and can introduce XS-Leaks. netlify.toml header edits only reach the edge after a Netlify "Clear cache and deploy".)

**AdSense is per-page (not a fixed tag on every page).** `templates/base.html` has an `{{ads_head}}` placeholder filled by `_ads_head()`/`post_ads_mode()` in `build.py`: the `/check/` tool and the **legal/trust pages** (about, privacy, cookies, terms, contact, disclaimer — via `render_simple_page(..., ads_mode="none")`) get **no ads**; debt/insolvency/recovery **and** sexual/sextortion/romance/identity-theft pages get **non-personalised ads** (`requestNonPersonalizedAds`, because Google restricts personalisation on these sensitive categories); everything else gets the standard Auto Ads tag. Tune the sensitive set via `_SENSITIVE_FINANCE_TERMS` (now also covers sextortion/deepfake/romance/identity terms; `post_ads_mode` normalises hyphens so hyphenated slugs match). Don't re-hardcode the ad tag in the template.

**Consent (UK/EEA):** ad + analytics consent is collected by **Google's certified CMP** (AdSense → Privacy & messaging, the "European regulations message"), which drives Google **Consent Mode** (both "advertising" and "analytics" consent-mode toggles are enabled in the dashboard). `assets/app.js` **defers** to it: when a TCF CMP is present (`window.__tcfapi`/`window.googlefc`), the custom cookie banner stays hidden (no double prompt) and the footer "Cookie settings" reopens the CMP; the **custom banner is only a fallback** for regions where Google's message isn't shown. (2026-06-24: the fallback now grants **advertising** consent only when it can positively confirm GDPR does not apply — `gdprApplies===false` from the TCF stub; otherwise it grants analytics only, so a CMP failure in the UK/EEA can't grant personalised-ad consent via the non-certified banner.) If the CMP is ever CSP-blocked, allow-list `fundingchoicesmessages.google.com` (mind the netlify.toml-headers-at-edge gotcha — Section 20 of `docs/project.md`).
